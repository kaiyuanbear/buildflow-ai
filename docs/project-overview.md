# BuildFlow AI 项目说明

## 1. 项目定位

BuildFlow AI 是一个面向面试演示的轻量 AI 应用构建器。用户用一句自然语言描述小型产品需求，系统会在服务端调用大模型，生成受约束的浏览器端应用文件；用户随后可查看 Agent 执行过程、检查生成文件、在隔离环境中交互预览，并保存、迭代和恢复项目版本。

项目关注的不是预置“简历 / Todo / 电商”等页面模板，而是建立一条通用、可验证的链路：

`产品提示词 → 可见 Agent 工作流 → 多文件应用产物 → 可交互预览 → 持久化版本`

该边界使项目既能体现 AI 产品能力，又能够在面试作业的时间与资源限制内保持可运行、可演示和可解释。

## 2. 主流程

### 2.1 初始化与账户

1. 首次访问时，用户使用邮箱和密码注册；注册页会在请求前校验两次密码是否一致。
2. 注册或登录成功后，服务端通过 HttpOnly JWT Cookie 建立会话。
3. 用户进入 Atoms 风格首页：左侧为账户、导航和可滚动的最近项目，中心区域用于输入产品需求。

### 2.2 生成应用

1. 用户输入例如“制作一个旅行行程编辑器”的需求并开始构建。
2. 系统创建私有项目与生成任务，跳转到三栏 Builder 工作台。
3. API 依次完成需求分析、应用蓝图生成、浏览器产物生成、安全/质量校验、文件保存和预览初始化。
4. 左栏显示真实、中文化且已持久化的 Agent 事件；中栏以文件树展示产物；右栏展示可操作的应用预览。

### 2.3 交互与持久化

1. 生成产物在 sandboxed iframe 内运行，用户可以使用其中的交互控件。
2. 预览的业务状态通过受控桥接保存为版本级状态；刷新页面后仍可恢复。
3. 项目、生成任务、日志、版本、文件和预览状态均保存于 PostgreSQL，且所有受保护接口校验项目归属。

## 3. 已实现的延展能力：自然语言迭代与版本恢复

在“输入提示词并获得可交互应用”的核心流程之外，BuildFlow AI 提供了版本化迭代能力：

1. 用户可在 Builder 左栏继续输入优化需求，例如“把布局改得更紧凑，并增加每周进度摘要”。
2. 系统会为该次优化创建新的不可变版本（v2、v3……），而不是覆盖旧结果。
3. 每个新版本保存初始需求及本次优化需求，Agent 时间线按版本顺序展示这些历史输入。
4. 用户可以查看任一版本的文件和预览，并将历史版本恢复为当前版本。
5. 预览交互状态与版本绑定，因此恢复版本后不会混用其他版本的状态。

这项能力将一次性生成结果延伸为可追溯、可比较、可回退的产品构建过程，也是本项目对应“至少一个延展或衍生能力”的主要交付。

## 4. 实现思路与关键取舍

### 4.1 通用生成，而非固定应用目录

系统不会根据关键词把提示词映射到固定的 Todo、简历或电商页面。DeepSeek 先返回应用蓝图，再返回受结构约束的浏览器文件产物；因此同一条管线能够处理不同类型的小型前端应用。

取舍是：生成对象限定为浏览器端静态应用，而不是任意全栈工程。这样避免在服务器执行不可信代码、安装依赖或维护子应用部署环境，换取安全性和演示可靠性。

### 4.2 多文件产物契约与质量门槛

新产物通常由 7–12 个文件构成：`index.html`、`README.md`、`styles/*.css` 与 `src/*.js`，并通过 manifest 指定 CSS 与 JavaScript 的加载顺序。API 会校验路径白名单、文件数量和大小、入口文件、外部资源、危险浏览器能力及最低质量门槛。

质量门槛要求应用具备多个页面区域、真实交互、初始演示数据、可见状态反馈与窄屏适配；若首次模型产物未通过，可进行一次受限修复。对于历史四文件版本，系统保留兼容预览路径。

### 4.3 安全隔离与密钥保护

- DeepSeek Key 仅保存在 API 服务端环境变量，浏览器、截图、日志和 Git 仓库均不可访问。
- 生成代码永不在服务器执行；预览只在 `sandbox="allow-scripts"` 的 iframe 中运行。
- CSP 与产物校验拒绝网络请求、外部资源、模块导入、`localStorage`、父窗口访问、Cookie 访问、弹窗等能力。
- PostgreSQL 层通过部分唯一索引限制同一项目仅有一个活动生成任务，避免并发生成竞争。

### 4.4 真实状态优先于“看起来像 AI”

左侧 Agent 栏展示的是服务端实际产生并保存的事件，例如模型请求、模型返回、质量校验、写入文件和保存版本；它不展示模型隐式思维链，也不伪造不存在的工具调用。模型不可用或产物不合格时，系统会明确显示本地可交互起步应用及原因，不把降级结果伪装成 AI 成功。

### 当前明确未做的内容

- 不执行任意生成代码，不安装生成项目的依赖，也不在服务端构建或发布生成的子应用。
- 不支持生成子应用后端、数据库、登录系统或一键部署。
- 不支持多人实时协作、分享评论、支付、插件、GitHub 同步和任务队列。
- 不暴露完整模型思维链；只保留可验证的执行摘要。
- 模型输出仍受网络、模型稳定性与时间预算影响，个别请求会进入明确标识的本地 fallback。

这些限制是当前作业的主动范围控制，而非将静态原型包装为完整生产平台。

## 6. 与评估维度的对应关系

### 完成度：功能完整性、稳定性与基本工程质量

项目具备真实账户、真实 API、真实数据库和真实可交互预览，不是纯静态页面。生成任务、文件和版本经刷新仍可读取；同项目并发生成受数据库约束；API 通过 Zod 在输入和模型输出边界进行校验。

### 工程思维：任务拆解、技术选型与复杂度控制

实现按“基础契约 → 认证与数据 → 首页与导航 → 生成管线 → 版本工作台 → QA 与部署”拆分。前后端保持包级分离，但生产环境以一个 Fastify 服务统一托管，降低 Cookie 跨域和双服务部署的风险。生成能力采用受约束的浏览器产物契约，避免引入不可信代码执行平台这一超出题目时间预算的复杂系统。

### 用户体验：流程清晰、反馈真实、结果可用

用户提交需求后立即进入工作台，构建过程、文件、版本和预览分别位于固定区域。构建过程中的信息为中文，并可看到输入的历史需求；预览不是截图，用户可直接操作并在刷新后验证状态。失败和 fallback 也会显示原因，避免不确定的空白结果。

### 创新性：亮点与可扩展潜力

亮点不在于预置页面数量，而在于“可验证的通用生成管线”：两阶段模型调用、结构安全校验、确定性质检、受控修复、隔离预览和版本化迭代共同构成了一条可复核链路。该设计可继续延伸为更高质量的生成、异步任务与协作能力，而无需回退到硬编码应用目录。

### 可交付性：运行、验证与部署

项目提供环境变量示例、数据库迁移、开发与生产构建命令、Dockerfile、部署说明、演示脚本及 QA 清单。生产环境使用单一来源承载前端与 API，便于面试官注册体验；Render 免费实例可能冷启动，首次访问应预留等待时间。

## 7. 后续投入计划与优先级

### P0：稳定演示主链路

优先处理公网可用性，而不是先堆叠新功能：增加错误监控、模型调用超时与重试策略、限流与调用额度控制，并完成每次部署后的新账户冒烟测试。理由是面试演示中，稳定地完成一次端到端生成比功能数量更重要。

### P1：提升长任务可靠性与生成质量

引入异步任务队列、流式进度、取消能力和失败恢复，解决模型生成时间较长时的请求可靠性问题；同时补充静态可访问性检查、截图评估和有限修复循环，提高页面质量的一致性。此阶段直接改善用户等待体验和生成结果质量。

### P2：提升产物可控性与复用性

引入设计令牌、受控组件片段、页面区域配置与安全的产物导出。目标是在不把系统退化为固定模板目录的前提下，给模型更稳定的视觉与交互约束，并允许用户带走生成结果。

### P3：协作与生态

在单用户主链路稳定后，再考虑分享链接、评论、多人协作、GitHub 同步和插件能力。这些能力需要额外的权限模型、审计与外部集成治理，当前不应抢占核心生成与可靠性工作。

## 8. 推荐演示顺序

1. 使用新邮箱注册，说明账户与项目数据是私有且持久化的。
2. 输入一个具体的小型产品需求，进入 Builder。
3. 展示中文 Agent 事件、文件树和右侧可操作预览。
4. 在预览中完成一次交互后刷新，确认状态仍在。
5. 输入优化需求，生成 v2；展示 Agent 历史需求、版本差异和版本恢复。
6. 简要说明安全边界：模型密钥只在后端、生成代码不在服务器执行、预览隔离运行。

这条演示路径同时覆盖了作业所要求的真实交互、数据持久化、基本使用流程与至少一个延展能力。
