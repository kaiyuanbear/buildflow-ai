# 多文件高质量应用产物设计

## 目标

BuildFlow AI 继续从任意小型产品提示词生成应用，而不是把提示词映射到固定的待办、简历或电商模板。本次调整让生成结果从“安全的单页起步应用”提升为“可查看、可交互、具有清晰结构的小型浏览器应用”。

成功标准：一个非降级生成通常包含 7–12 个源文件、至少 5 个可见区域、至少 4 个可验证的本地交互，以及可在桌面和窄屏使用的视觉层级。它不追求复刻 Atoms 的完整工程系统、在线文件管理或任意依赖安装。

## 已确认约束

- DeepSeek 仅由 API 服务调用；密钥、系统提示词和隐藏推理不可暴露给浏览器。
- 生成代码绝不在服务端执行；预览仅在 `sandbox="allow-scripts"`、不透明源的 iframe 中运行。
- 预览 CSP 保持禁止网络、外部资源、表单提交、弹窗和父窗口访问。
- 不允许 `fetch`、WebSocket、`localStorage`、`sessionStorage`、`import`、外部 URL、`window.open`、`parent`、`top` 或 `document.cookie`。
- 用户只可访问自己的项目、任务、版本、文件和预览状态；一个项目同一时刻只能有一个生成任务。
- 已有四文件版本和历史任务日志必须仍可读取与预览。

## 方案选择

### 方案 A：保留四文件，仅增加 token

实现最小，但模型容易把预算花在冗长文案或单一大文件上；文件查看器仍无法呈现接近真实项目的组织结构，也没有可靠质量下限。

### 方案 B：多文件静态产物与确定性预览组装（选择）

模型生成一个受限 `manifest` 和 7–12 个 HTML、CSS、JS、Markdown 文件。服务端和前端只进行字符串级的白名单验证与确定性顺序组装，不执行模型代码。预览把多个样式表和脚本按 manifest 顺序内联到现有 iframe `srcDoc`。

这提供接近小型前端项目的文件树和更清晰的职责划分，同时不需要 Node 构建、包管理器、ESM 模块解析或子应用部署。

### 方案 C：生成任意 React/Vite 工程并在服务端构建

视觉上最接近 Atoms 的文件列表，但需要执行不可信构建脚本、安装依赖、隔离容器、资源配额和错误恢复。这违背当前安全边界，不纳入面试作业。

## 产物契约

新版本的模型响应包含：

```ts
{
  appSpec: { appName, tagline, features, preview: { entryPath: "index.html" } },
  manifest: {
    styles: ["styles/tokens.css", "styles/layout.css", "styles/components.css"],
    scripts: ["src/state.js", "src/data.js", "src/ui.js", "src/app.js"]
  },
  files: [
    { path: "index.html", language: "html", contents: "..." },
    { path: "styles/tokens.css", language: "css", contents: "..." },
    { path: "src/app.js", language: "js", contents: "..." },
    { path: "README.md", language: "md", contents: "..." }
  ]
}
```

允许的路径：根目录的 `index.html`、`README.md`，以及 `styles/*.css`、`src/*.js`。每个路径只能出现一次，文件数量为 7–12，单文件不超过 40 KB，所有文件总计不超过 180 KB。`manifest` 必须引用全部且仅引用对应的 CSS/JS 文件，且顺序是预览唯一的加载顺序。

不使用 `script src`、`link href`、CSS `url()` 或 JavaScript 模块导入。HTML 是结构与语义入口；CSS 拆为设计令牌、布局和组件；JS 拆为状态/示例数据/渲染与交互/启动逻辑。生成的 JS 共享 iframe 全局作用域，但只通过 `window.__BUILDFLOW_INITIAL_STATE__` 读取初始状态，并通过 `window.__BUILDFLOW_SAVE_STATE__(state)` 保存编辑后的状态。

旧版四文件产物没有 `manifest` 时，系统按旧顺序 `styles.css`、`app.js` 预览，确保历史版本可用。

## 生成与质量流程

```text
提示词
  -> 产品蓝图（页面区域、数据实体、交互、视觉方向、复杂度目标）
  -> 多文件产物请求
  -> 结构与安全校验
  -> 确定性质检
  -> 仅一次受限修复（如需）
  -> 保存文件、版本与隔离预览
```

蓝图新增 `complexityTarget`：页面区域、交互、数据实体和响应式要求。它不绑定某个应用品类，而是把用户需求转换为可验证的实现规模。

确定性质检至少检查：

- 5 个以上语义或视觉区域；
- 4 个以上用户可触发的交互处理器；
- 一个或多个初始数据实体，首屏不是空状态；
- 至少一个会随状态变化的统计、进度、筛选结果或详情面板；
- CSS 具备布局规则和窄屏媒体查询；
- `manifest`、文件数量、文件路径和引用顺序完整。

质检失败不会放宽安全规则。系统将把具体缺口转化为中文事件，例如“质量校验：缺少窄屏布局与状态统计”，并向模型发起一次完整替换请求。第二次仍不合格，才明确保存本地起步应用及原因。

## 预算与可靠性

- 蓝图：非思考 JSON，最多 2,500 tokens；
- 主产物：非思考 JSON，最多 18,000 tokens；
- 修复：非思考 JSON，最多 18,000 tokens；
- 单次模型请求最多 100 秒；整个生成任务最多 300 秒；
- 低于剩余安全时间时跳过修复并如实降级；
- 仍只有一次修复机会，避免不可控成本和长时间等待。

这些数值适合面试演示：可生成明显更丰富的小型应用，但不会试图产出完整商业项目。

## Builder 体验

左栏继续展示真实且中文化的 Agent 事件。新增可见阶段包括“复杂度规划”和“质量校验”，但不展示模型隐式推理。

中栏从平铺文件名升级为可展开的路径树，仍可选择任一文件查看源代码；版本历史、恢复和当前版本语义不变。右栏使用 manifest 拼装的隔离预览，保持现有状态桥接与错误提示。

## 失败处理

- 模型 JSON 无法解析、文件路径非法、安全能力违规、总大小超限、质量不足、超时或长度截断：记录中文化的真实原因。
- 安全或质量校验失败：仅能请求一次完整替换产物，不拼接两份模型输出。
- API 密钥缺失或模型不可用：保存明确标注的本地起步应用，而不声称 AI 已成功生成。
- 历史版本缺少 manifest：使用旧四文件兼容渲染路径。

## 验收与测试

API：覆盖 manifest 解析、路径白名单、顺序/重复检测、安全词扫描、质量缺口、一次修复、超时降级、所有权和旧版兼容。

浏览器：覆盖多级文件树、生成中的中文事件、至少一个预览交互、状态刷新持久化、版本恢复和窄屏布局。

基准提示词：一个数据/效率工具、一个表单或编辑器、一个展示型网站。每个非降级结果必须通过质量门槛；不对具体页面类型做硬编码断言。
